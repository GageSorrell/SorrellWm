# `electron-reactive-event-cli`

**Purpose.**&ensp;This article describes the helper package `electron-reactive-event-cli`.
Using this package is optional, but it will write all the basic boilerplate code needed to set up your project to use `electron-reactive-event`.
An additional command is provided to help register your event types as you define events throughout the development of your project.

For a thorough explanation of *what* boilerplate is needed, *why* it is needed, and *how* you can customize it, see [the Setup article](./Setup.md).

> [!NOTE] *"Why is (almost) every feature exposed via a factory function, and not exported directly?"*
>
> This is done to make type definitions less intrusive: you provide
> to these factory functions your `IMainRegistrar` and `IRendererRegistrar` types, and all returned functions will be type-aware for your app's events.

## Commands

There are six commands:

* three commands help with initial setup (`main`, `preload`, and `provider`)
* `register` helps manage event declarations as they continue to be created during development
* `setup` provides an interactive wizard that combines the three setup commands, and `register --create-json`.
* the sixth command is `help`.

The three setup commands take the same arguments, detailed at the end of this subsection.

### The `setup` Command&ensp;*(Recommended)*

This command takes no arguments, and provides an interactive wizard, which prompts the user for each argument for each of the three setup commands and the `register --create-json` command.

It is recommended that you use this command, but the three setup commands are provided for a traditional workflow.

### The `main` Command

This command writes the boilerplate needed for the functions used in `main`.
These mirror the familiar API surface of `ipcMain`, and comprise the simplest boilerplate of the provided commands.

**TL;DR.**&ensp;A call to `GetMainReactiveEventFunctions` is generated, using your registrar types.
The output is `export`ed for you to use throughout your codebase.

*See [Setup § Main](./Setup.md#Main) for an in-depth explanation of what this package provides to `main`, and how it can be customized.*

### The `renderer` Command

This command writes the boilerplate needed to make use of the `ipcRenderer` functions exposed to the renderer.
To see how you might want to modify this boilerplate, please see , which explains how `electron-reactive-event` intends for the `ipcRenderer` API to be wrapped and safely exposed to the `renderer`.

*See [Setup § Renderer](./Setup.md#Renderer) for an in-depth explanation of what this package provides to the `renderer`, and how it can be customized.
Also see [Setup § Preload](./Setup.md#Renderer) to understand how `electron-reactive-event` intends for the `ipcRenderer` API to be safely exposed to the `renderer`.*

### The `preload` Command

This command writes the boilerplate needed for getting the relevant surface of the `ipcRenderer` API into the renderer.
The package's author anticipates that projects integrating `electron-reactive-event` will vary most in the way that they expose functionality (preload scripts *et al.*) *wrt* what `electron-reactive-event` touches in the consuming codebase.

As a result, the code generated by this command is intended to be a reasonable *middle-ground* solution, which you will likely modify to some extent.
This is in contrast to the other commands, whose output should be sufficient *as-is* for most use-cases.

*See [Setup § Preload](./Setup.md#Preload) for an in-depth explanation of what `preload` work must be done to implement `electron-reactive-event`, and how your `preload` logic can be customized.*

### Setup Arguments

The commands `main`, `renderer`, and `preload` all take the same arguments.

#### `--output <value>`&ensp;*(Required)*

|     `<value>` | Description                             |
|-------------: | :---------------------------------------|
|   `clipboard` | Writes the output to the clipboard      |
|     `console` | Writes the output to `stdout`           |
| `file <path>` | Writes the output to a file at `<path>` |

#### `--{main|renderer}-registrar <type name> <path>`&ensp;*(Optional)*

The name and path containing your `main` or `renderer` registrar type.
If this argument is *not* used, and `--yes` is not also provided, then the user will be prompted interactively to select the module that contains the relevant registrar type.
Upon selecting the desired module, a list will be displayed, from which the user selects the desired registrar type.
If you specify a value for one of these (interactively or via the flag), then you likely want to provide the *other* registrar type as well.

To simplify the implementation of this package, if this flag is used, then it must be provided *both* `<type name>` and `path` with the flag.

#### `--yes`&ensp;*(Optional)*

When this flag is used, if either of `--{main|renderer}-registrar` is not provided, then the user will *not* be prompted for the value(s) interactively, and instead temporary registrar types `IMainRegistrar` and `IRendererRegistrar` will be defined and used in the output.
If this argument is used, then you will need to replace references to these with your real registrar types.

### The `register` Command

The user must create two interfaces to use `electron-reactive-event`: one interface for events sent from `main`, and one interface for events sent from the `renderer`.
To accommodate the breadth of mature codebases, these interfaces, usually defined with no contents, are extended via `declare module`.
While this allows for flexibility across the codebase, `declare module` blocks are somewhat verbose to type out manually.

This tedium is addressed by the `register` command, which creates and maintains these `declare module` blocks for you.

#### `--create-json <path` *optional* `>`&ensp;*(Optional)*

If this flag is provided, then all other flags are ignored.
A JSON file is written, in which the user can specify the arguments provided to this function.
This is the intended workflow for long-term use of `electron-reactive-event`.

If a `<path>` is *not* provided, then the file is written to `electron-reactive-event.json`, in the package's root directory.

If a `<path>` *is* provided, then the file will be written to that path, and a `config` property is created in your `package.json` specifying this path.

Specifically, the relevant portion of your `package.json` will look like

```jsonc
    // ...
    "config": {
        "electron-reactive-event-cli": "<path>",
        // ...
    },
    // ...
```

#### `--path <path>`&ensp;*(Optional)*

The path to the JSON file created with `--create-json`.
If no path is specified, then the package will look for a path specified in the project's `package.json` `config` property.
If the relevant `config` property is not found, then the CLI will attempt to load the path `./electron-reactive-event.json`.

This flag may not be used with any other flag.

#### `--{main|renderer}-registrar`&ensp;*(Again)*

*This is identical to [the flag above of the same name](#--mainrenderer-registrar-type-name-pathoptional).*

#### `--ownership <value>`&ensp;*(Required)*

This determines how `electron-reactive-event-cli` will determine the [ownership](./Glossary.md#ownership) for each event declaration.

|     `<value>` | Identification Strategy                 |
|-------------: | :---------------------------------------|
|       `jsdoc` | The ownership of event declarations will be determined<br />by the existence of JSDoc comments containing<br />`@MainEventDecl` or `@RendererEventDecl`. |
|       `jsdoc <main flag> <renderer flag>` | Identical to `jsdoc`, but the user specifies the `@`-prefixed<br />words that identify the ownership of the event (*i.e.*, `main`<br />*versus* `renderer`).  The `@` prefix will be added, if missing. |
|     `globs <main glob> <renderer glob>` | Types defined with `EventDecl` in files matching `<main glob>` and `<renderer glob>` are identified as `main`/`renderer` events respectively. |

If `globs` is used, then if a given file matches one of the globs, but not the glob specified under `--files`, then the file will be ignored.

> [!NOTE]
> If you have a `declare module` block in which you register event declarations but want the `electron-reactive-event-cli` to *ignore*, then create a JSDoc comment above the `declare module` statement containing `@EventCliIgnore`.

#### `--files <glob>`&ensp;*(Optional)*

Specify the files in which the CLI will look.
If not specified, all `*.ts` files in the project will be used.

#### `--dry-run`&ensp;*(Optional)*

No files will be created, removed, or modified.
You likely want to use `--verbose` with this flag.

#### `--verbose`&ensp;*(Optional)*

The paths of affected files are written to the terminal, as well as a description of the relevant types in their respective files, and what is done with them.

Each type that is defined with `EventDecl` will be recognized, and will have exactly one of the following statuses assigned in the terminal output,

* Now added to a new `declare module` block
* Now added to an existing `declare module` block
* Unmodified (already exists in a `declare module` block)

Types that *were* in an affected `declare module` block, but were removed, will also be listed.

#### Suggested Usage: `package.json` `script`

Since the `register` command is intended to be used frequently during development, a workflow for doing so is suggested below.

First, it is suggested that you add `electron-reactive-event-cli` as a `devDependency` of your project.

```bash
npm install --save-dev electron-reactive-event-cli
```

Otherwise, you may use this workflow, but with `npx electron-reactive-cli` used in place of `npm electron-reactive-cli`.

Then, create a JSON file via `npx electron-reactive-event-cli register --create-json`, and fill out the template file written (by default, this is `electron-reactive-event.json` in your project's root directory).

Then, add a `script` to your `package.json`, such as

```jsonc
    // ...
    "scripts": {
        // ...
        "register-events": "npm electron-reactive-cli",
        // ...
    },
    // ...
```

If your JSON file is not at the default path, then be sure to specify this in the `script` with the `--path` flag or in the `config` property in your `package.json`.

Then, it is recommended to call this `script` within any `build` or `prestart` `script` that your project has.
